# BionicPRO — Спринт 9, задание 1, задача 1

## Архитектурные решения

1. **BFF.** Браузер обращается только к BFF через HTTPS и получает непрозрачную серверную cookie с атрибутами `Secure`, `HttpOnly`, `SameSite=Strict` (при совместимом UX и маршрутами перенаправления; иначе обоснованный Lax), `Path=/`, без `Domain`. Рекомендуется `__Host-`-префикс. Никакие access/refresh токены Identity Provider не передаются в JS, localStorage, sessionStorage или в ответ API. Для Android/iOS может использоваться региональный mobile-BFF с непрозрачной сессией и нативным защищённым хранилищем; токены IdP не должны поступать в приложение. Не смешивать cookie и IdP JWT.
2. **OAuth 2.0.** BFF — confidential client в Keycloak. Code + PKCE (`S256`); `state`, `nonce` (OIDC), строгие redirect URI, защита от login CSRF, проверка `iss`, `aud`, `exp`, подписи. Обмен `code` на токены происходит только между BFF и Keycloak, в пределах региона. Refresh token хранится шифрованным и привязанным к серверной сессии; реализовать ротацию и revoke по выходу, idle/absolute session timeouts.
3. **Federation.** Keycloak RU подключается к локальному OIDC/SAML IdP (Identity Brokering) либо к локальному LDAP/AD через LDAPS (User Federation). Внешний источник остаётся системой записи для учётных данных. Для LDAP использовать `Import Users=OFF` там, где допустимо; понимать, что при Identity Brokering Keycloak может сохранять локальную *минимальную* запись связанной идентичности. Никаких пользовательских паролей в BionicPRO; роль и нужные технические идентификаторы ограничить минимально необходимыми.
4. **Страны.** Отдельный Keycloak/realm, BFF, хранилище сессий и identity DB для каждой страны. CRM, медицинские записи и телеметрия также хранятся локально. Global policy/IaC передаются как настройки без ПДн. Выбор региона по правовому основанию/домашнему региону аккаунта, а не только по IP. Межрегиональную передачу ПДн не использовать по умолчанию; возможные исключения — только после юридической оценки. Идентификация пользователя: `(country, issuer, sub) → local internal_user_id` (псевдонимный идентификатор в локальной БД), не полагаться на совпадение email.
5. **Авторизация.** Keycloak выдаёт базовые роли (например, `user`, `administrator`, `prothetic_user`), но Reports API *на каждый запрос* проверяет: (а) допустимую роль/scope; (б) ownership: `current_user_id` имеет право на `prosthesis_id` по данным локальной CRM. Не доверять `user_id`, `prosthesis_id` или owner из клиентского запроса без проверки. Использовать deny-by-default, постраничную выборку только своих записей, исключать IDOR/BOLA.
6. **Контроль угроз.** HTTPS/TLS, LDAPS, vault для secrets, SSO session revocation, rate limiting, CSRF-проверки для cookie-сессий, аудит попыток доступа (без чувствительного payload), безопасные CORS-правила (не `*` с credentials), CSP, secure headers, mTLS или защищённая внутренняя сеть. Разделить полномочия admin и пациента. Старые сессии/токены после инцидента необходимо отозвать. PKCE не заменяет защиту API и управление правами.

## Локализация, аутентификация, авторизация — разные понятия

- **Аутентификация:** кто пользователь? Региональный Keycloak + внешний региональный источник.
- **Авторизация:** к какому отчёту у него есть доступ? Сервис Reports API + CRM ownership.
- **Локализация данных:** в какой юрисдикции хранятся/обрабатываются учётные, персональные и медицинские данные? В пределах регионального контура, включая логи, бэкапы и сессии.

## Сценарий входа в веб-приложение

1. `GET /auth/login` → BFF создаёт `state`, `nonce`, `code_verifier`, `code_challenge=S256(verifier)` и привязывает к краткоживущей предварительной сессии.
2. BFF перенаправляет браузер на региональный Keycloak `/authorize`.
3. Keycloak через Identity Brokering направляет пользователя в региональный внешний IdP (OIDC/SAML) либо проверяет пароль по региональному LDAP/AD. Browser может проходить перенаправления, но токены IdP в React не поступают.
4. Keycloak перенаправляет браузер на строго зарегистрированный callback BFF с одноразовым `code` и `state`.
5. BFF проверяет `state`, issuer (если применяется), `nonce` у ID-токена, передаёт `code_verifier` и client authentication в `/token` Keycloak.
6. BFF валидирует токены, сохраняет access/refresh серверно и отдаёт клиенту только непрозрачную cookie с session ID.
7. Клиент вызывает `GET /api/reports` с cookie. BFF проверяет сессию, CSRF и forward-запрос в Reports API с нужными серверными полномочиями. API проверяет подпись/claims access token, роль, scope и владение протезом по CRM.
8. При истечении срока действия access token BFF выполняет refresh сервер-сервер. Logout отзывает refresh-токены и уничтожает сессию.
